1. Scope of Testing

1.1 Target of Test

The target system is an online auction platform (BidNow) for buying and selling products through auction mechanism. The functional testing focuses on verifying that each feature operates correctly as described in the Business Rules Documentation:

● User Authentication & Authorization (Register, Login, Email Verification, Password Reset, Role Management)
● Product/Item Management (Create, Edit, Delete, Approve/Reject, Draft Management)
● Auction Management (Create Auction, Place Bid, Auto-Bid, Buy Now, Auction Status Management)
● Order & Payment Processing (Order Creation, Payment Link Generation, Payment Webhook Handling, Shipping Info Update, Order Confirmation)
● Dispute Resolution (Create Dispute, Handle Dispute, Dispute Chat)
● Messaging System (Send Message, Get Conversations, Mark as Read, Auction Chat)
● Notifications (Create, Get, Mark as Read, Real-time Notifications)
● Ratings & Feedback (Create Rating, Get Ratings for User/Auction)
● Watchlist & Favorites (Add/Remove Watchlist, Add/Remove Favorite Sellers)
● Search & Filter (Search Items, Filter Auctions, Category-based Search)
● Admin Dashboard (Product Approval, Auction Management, User Management, Statistics)
● Real-time Features (SignalR for Live Bidding, Real-time Price Updates, Live Chat)
● AI Recommendation System (Personalized auction recommendations based on user behavior, bidding history, watchlist, search keywords)

Out of scope:
● Third-party services' internal logic (PayOS Payment Gateway, Email Service, File Upload Service) – only integration responses are tested.
● Cross-browser UI compatibility (tested on Chrome only).
● Performance testing under extreme load conditions.
● Security penetration testing (handled separately).

2. Test Strategy

2.1 Testing Types

2.1.1 White-box Testing
- Objective: Verify individual units (controllers, services) work correctly in isolation
- Technique: White-box testing with mocked dependencies using Moq framework, boundary value and equivalence class testing
- Completion Criteria: 82 unit tests implemented covering 8 controllers (AuthController, AuctionsController, CategoriesController, MessagesController, AdminAuctionsController, AdminStatsController, AuctionMessagesController, UsersController). All tests pass consistently.

2.1.2 Functional Testing
- Objective: Verify functional requirements are implemented correctly through unit tests
- Technique: Black-box testing approach via unit tests, testing valid/invalid inputs, edge cases, exception scenarios
- Completion Criteria: Critical business logic methods tested, edge cases and exception scenarios covered, test cases follow AAA pattern (Arrange-Act-Assert).

2.1.3 Regression Testing
- Objective: Ensure new changes do not break existing functionality
- Technique: Automated test suite execution via dotnet test command after code changes
- Completion Criteria: All 82 existing test cases pass after code changes, no new defects introduced.

2.1.4 Acceptance Testing
- Objective: Validate that the system meets user requirements and is ready for production deployment
- Technique: User Acceptance Testing (UAT) with real users, business scenario validation, production readiness testing
- Completion Criteria: All acceptance criteria are met, stakeholders approve system for production deployment, critical business workflows validated in production-like environment.

4. Test Cases

4.1 Unit Test Cases

Focuses on validating individual units (controllers, services, methods) in isolation with mocked dependencies.

Test Basis
- Business Rules Documentation
- Controller method specifications
- Service interface contracts
- Exception handling requirements

Techniques
- White-box testing: Test internal logic and code paths
- Mocking: Use Moq framework to isolate dependencies
- Boundary value testing: Test input boundaries and edge cases
- Equivalence class testing: Group similar inputs for testing
- Exception testing: Verify error handling scenarios

Objectives
- Ensure individual methods return correct results for valid inputs
- Validate error handling for invalid inputs and edge cases
- Confirm business logic implementation matches requirements
- Verify proper use of dependencies through mocks

Output
Unit Test Excel, organized by controller (AuthController, AuctionsController, CategoriesController, MessagesController, AdminAuctionsController, AdminStatsController, AuctionMessagesController, UsersController). Total: 82 test cases.

4.2 Integration Test Cases

Focuses on validating the interaction between multiple modules and ensuring that data flows correctly across the system layers.

Test Basis
- SRS – Software Requirement Specification
- Database schema & data flow
- Business Rules
- API endpoint specifications

Techniques
- Functional Testing (Black-box): Validate integration between FE requests and BE responses
- Data-flow testing: Ensure data created in one module is propagated to the next
- Interface testing: Validate communication between internal modules and external services (e.g., PayOS, Email Service, SignalR)

Objectives
- Ensure that connected modules operate correctly together
- Validate database updates across integrated components
- Confirm consistent role-based behavior across modules
- Verify external service integrations (PayOS webhook, Email notifications, SignalR real-time updates)

Output
Integration Test Excel, organized by module interactions (Authentication ↔ Database, Auction ↔ Payment, Order ↔ Notification, SignalR ↔ Auction Updates, etc.).

4.3 System Test Cases

Focuses on validating end-to-end user workflows and complete business scenarios from user perspective.

Test Basis
- User stories and use cases
- Business Rules Documentation
- Complete workflow specifications
- User acceptance criteria

Techniques
- End-to-end testing: Complete user journeys from start to finish
- Scenario-based testing: Test real-world user scenarios
- Business rule validation: Verify all business rules are enforced correctly
- Workflow testing: Validate complete processes (register → create product → create auction → bid → payment → order completion)

Objectives
- Ensure complete user journeys work correctly end-to-end
- Validate all business rules are enforced across the system
- Confirm system handles concurrent users and real-time updates correctly
- Verify error handling and edge cases in complete workflows

Output
System Test Excel, organized by user workflows (Buyer Journey, Seller Journey, Admin Workflows, Payment Flow, Dispute Resolution Flow, etc.).

4.4 Acceptance Test Cases

Focuses on validating that the system meets user requirements and is ready for production deployment from stakeholder perspective.

Test Basis
- User requirements and acceptance criteria
- Business Rules Documentation
- Stakeholder expectations
- Production readiness checklist

Techniques
- User Acceptance Testing (UAT): Real users test the system in production-like environment
- Business scenario validation: Verify system meets business objectives
- Usability testing: Ensure system is intuitive and user-friendly
- Production readiness testing: Validate system is ready for live deployment

Objectives
- Confirm system meets all user requirements and acceptance criteria
- Validate system is ready for production deployment
- Ensure user experience meets stakeholder expectations
- Verify all critical business workflows function correctly in production-like environment

Output
Acceptance Test Excel, organized by user roles and acceptance criteria (Buyer Acceptance Tests, Seller Acceptance Tests, Admin Acceptance Tests, Payment Acceptance Tests, etc.).

4.5 AI Test Cases

Object
Focuses on validating AI recommendation system accuracy, relevance, and correctness of returned results.

Test Basis
- AI Recommendation Service specifications
- Vector similarity search requirements
- User behavior data (bidding history, watchlist, search keywords, viewed auctions)
- Pinecone vector database integration

Techniques
- Functional Testing (Black-box): Test AI recommendation API endpoints and validate returned results
- Accuracy testing: Verify recommendations match user interests based on historical data
- Relevance testing: Validate similarity scores and ranking of recommended auctions
- Fallback testing: Test behavior for new users without history
- Data validation: Ensure recommendations only include active auctions

Objectives
- Ensure AI recommendations are relevant to user interests based on bidding history, watchlist, search keywords, and viewed auctions
- Validate that recommendations only show active or scheduled auctions with valid end times
- Confirm similarity scores are calculated correctly and results are sorted appropriately
- Verify fallback mechanism works correctly for new users without activity history
- Test recommendation result count limits (default 4, maximum 24)

Output
AI Test Excel, organized by test scenarios (User with History, New User Fallback, Bidding History Based, Watchlist Based, Active Auctions Filter, Result Count Validation). AI recommendations are relevant to user interests; recommendations only show active auctions; similarity scores are accurate; fallback works for new users.
